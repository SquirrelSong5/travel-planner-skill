# 分阶段迭代

分轮用于尽早淘汰错误，不是把同一套检查重复三遍。

## Round 1：结构

目标：确认方案骨架可继续研究。

- V0 核心字段；
- V1 区域一致性；
- V4 预约密度；
- V11 预订链接。

先修日期、区域、重复序号、缺坐标和错误链接。

本轮先用小红书建立目的地候选与体验风险，再用官方渠道淘汰不开放、不可预约或规则冲突的候选。

## Round 2：时空

目标：确认真实路线与返程安全。

- V0 核心字段；
- V2 通勤粗算；
- V5 返程缓冲；
- V8 路线来源字段；
- V9 时长下限；
- V13 酒店往返。

这一轮必须拿到主要移动段的地图查询结果，不能靠“看起来很近”。

本轮以高德为主，把候选真正落到坐标、顺序和移动时间上。

## Round 3：体验与预算

目标：补齐餐饮、天气和价格证据。

- V0 核心字段；
- V3 餐厅区域；
- V6 天气备选；
- V8 路线字段复核；
- V10 价格溯源。
- V12 信息时效性与行前复核。

最后再人工核对用户禁忌（V7）、结构化 Plan B、安全提醒与最新官方通知。

本轮用美团围绕已确定区域建立餐厅候选，用 OTA 核对酒店、票务、价格和可订状态；餐厅位置仍交回高德确认。

## 全量收口

无论分轮结果如何，交付前都运行：

```bash
python scripts/validate.py trip.json --pretty --fail-on-warn
```

增量修改时可以先跑受影响的轮次，但最终仍需全量收口。

同时检查 `source_coverage` 是否包含官方、高德、OTA、小红书和美团五项，以及未使用项是否如实说明原因。
