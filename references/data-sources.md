# 信息源与证据规范

本项目把信息源分为五类。来源的职责不同：官方渠道回答“能不能去”，地图回答“在哪里、怎么走”，OTA 回答“能不能订、多少钱”，攻略回答“体验可能怎样”。

## 优先级

同一事实冲突时，按以下顺序处理：

1. 当事机构或运营方的最新公告；
2. 政府、铁路、航司、机场、景区和场馆官方渠道；
3. 高德地图、国内 OTA 等结构化平台；
4. 美团攻略等编辑型内容；
5. 小红书等用户经验内容。

低优先级来源不能覆盖高优先级硬事实。攻略称“免预约”，而官方页要求预约时，以官方页为准并记录冲突。

## 分阶段协作

完整行程默认逐一尝试五类来源。阶段代表平台最擅长解决的问题，不代表证据优先级：小红书可以最先用于发现，但不能覆盖后查到的官方规则。

| 阶段 | 主平台 | 解决的问题 | 与其他平台的交接 |
| --- | --- | --- | --- |
| 1. 目的地发现 | 小红书 | 最近大家怎么玩、如何分区、何时拥挤、有哪些体验风险 | 只建立候选，不直接写成硬事实 |
| 2. 规则确认 | 官方与运营方 | 是否开放、是否预约、票务与临时通知 | 淘汰与官方规则冲突的候选 |
| 3. 路线落地 | 高德地图 | 候选在哪里、顺不顺路、移动需要多久 | 把可用候选排成现实日程 |
| 4. 餐饮筛选 | 美团攻略 | 当日区域附近吃什么、适合什么预算和场景 | 候选再交给高德确认位置 |
| 5. 交易核对 | 携程等国内 OTA | 酒店、机票、火车、门票是否可订以及当前价格 | 写入预订状态、截止时间与价格区间 |
| 6. 交付前复核 | 官方 + 高德 + OTA | 开放、路线、末班、价格与可售状态是否变化 | 更新行程并设置下次复核时间 |

每类平台在 `source_coverage` 中只保留一项，可包含多个阶段：

```json
{
  "platform": "xiaohongshu",
  "status": "used",
  "stages": ["discovery", "experience"],
  "purpose": "发现近期分区、排队和避雷信号",
  "checked_at": "2026-08-24T15:30:00+08:00",
  "source_refs": ["https://www.xiaohongshu.com/..."],
  "note": "只作为体验信号"
}
```

`status` 使用 `used`、`degraded`、`unavailable` 或 `not_applicable`。完整多日攻略应尽量让五项都是 `used`；来源不可用或任务确实无对应需求时，必须记录原因和影响，不能为了显示“五源齐全”伪造访问痕迹。

## 五类来源

### 1. 高德地图

适合：

- POI 名称、地址、坐标和地理编码；
- 周边搜索与距离；
- 步行、骑行、公交和驾车路线；
- 主要移动段时长。

要求：

- 保存查询所得的 `duration_min`，不要根据直线距离伪装成实算；
- `source` 可写 `amap-mcp` 或 `amap-rest-api`；
- 记录能回溯到查询对象的 `source_ref`；
- 高德中的营业时间可能滞后，关键场馆仍需官方确认。

### 2. 官方与运营方渠道

适合：

- 开放时间、闭馆日、临时关闭；
- 预约入口、实名规则、放票时间；
- 门票、优惠政策、行李和安检规则；
- 公共交通运营通知；
- 旅行日期对应的天气或预警。

网页搜索是发现工具，不是最终来源。尽量打开并引用原始官方页面；搜索摘要无法确认时标为待核验。

## 检索方式不是信息源

网页搜索、浏览器、WebFetch、MCP 和 REST API 说明“如何取得信息”；上述五类来源说明“信息由谁提供”。证据字段记录最终发布者与原始页面，必要时再在 `source` 中区分 `amap-mcp`、`amap-rest-api` 等技术路径。不要把 `web-search` 单独列成事实来源。

### 3. 携程等国内 OTA

适合：

- 酒店、机票、火车候选；
- 查询时点的价格区间和房型/舱位可售状态；
- 国内可访问的预订深链。

要求：

- 价格必须标查询日期、人数、晚数或张数；
- 优先 `ctrip.com` 国内链接，禁止自动改成 `trip.com`、Booking、Agoda 等国际 OTA；
- OTA 信息与运营方冲突时，硬规则以运营方为准；
- 不能拿示例价格或模型记忆标成 `ctrip-webfetch`。

### 4. 小红书

适合：

- 城市分区、游玩节奏和拍照时段；
- 近期排队、拥挤、施工、体感和踩雷；
- 发现官方页未描述的体验问题。

要求：

- 作为可选软信号，不阻塞基础行程；
- 关注发布时间和多个独立帖子的一致性；
- 把“有人这样体验”与“客观事实”分开表达；
- 不要求登录、扫码或绕过访问限制。

### 5. 美团攻略

适合：

- 建立餐厅候选池；
- 按菜系、区域、预算和用餐场景筛选；
- 补充本地代表性餐饮方向。

要求：

- 候选最终用地图确认位置；
- 营业状态与价格仍应交叉验证；
- 页面不可用时降级到地图 + 网页搜索，不反复绕过限制。

## 大众点评的位置

大众点评不是默认信息源。用户明确要求点评榜单或评价信号，且当前环境已有合法访问能力时，可以补充；否则跳过。不得强制安装扩展、要求扫码登录、规避验证码或声称访问了实际未访问的页面。

## 证据字段

会变化的事实建议至少保存：

```json
{
  "source": "official-site",
  "source_ref": "https://example.org/notice/123",
  "checked_at": "2026-08-24T15:30:00+08:00",
  "note": "周一闭馆；节假日另行公告"
}
```

价格对象至少保存：

```json
{
  "min": 300,
  "max": 420,
  "currency": "CNY",
  "unit": "per_night",
  "quantity": 2,
  "total_min": 600,
  "total_max": 840,
  "source": "ctrip-webfetch",
  "source_ref": "查询条件与国内页面链接",
  "checked_at": "2026-08-24"
}
```

## 降级规则

| 缺失能力 | 可以继续做 | 必须标注 |
| --- | --- | --- |
| 无地图查询 | 官方事实、候选池、粗排日程 | 路线与时长待核验 |
| 无 OTA | 路线与体验规划 | 价格/可售未知，不给假区间 |
| 无小红书 | 完整基础行程 | 缺近期用户体验信号 |
| 无美团攻略 | 用地图和网页搜索找餐厅 | 候选池来源改变 |
| 无公开发布能力 | 生成本地 Markdown/HTML | 不承诺公开 URL |

任何降级都不允许把 `estimate`、`demo-estimate`、`memory` 或 `note-derived` 改名成真实来源以通过校验。
