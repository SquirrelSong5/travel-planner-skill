# 多轮修改协议

## 首次规划

1. 复述目的地、日期、人数和硬约束；
2. 只追问会改变结果的缺项；
3. 说明可用与缺失的信息源；
4. 根据距离出发的天数执行对应强度的行前复核；
5. 完成研究和校验，从同一份 JSON 渲染 Markdown 与 HTML；
6. 把 Markdown 完整放进对话并同时交付 HTML 文件；公开发布另行确认。

不要把环境配置变成旅行规划的强制前置。可选来源缺失时可以降级，路线硬数据缺失时必须明确“待核验”。

## 修改已有方案

收到“换酒店”“删景点”“加一天”等请求时：

1. 读取当前 JSON，不从聊天摘要重建；
2. 列出直接受影响的日期和依赖项；
3. 只重新查询失效的坐标、路线、价格和预约；
4. 保留无关用户选择与来源；
5. 更新受影响的 `prebook`、`plan_b`、`safety_notes` 与 `rechecks`；
6. 全量校验，重新生成 Markdown 并重渲 HTML；
7. 在同一次回复中重新交付两个最新版本；
8. 只有用户要求同步时才更新公开页面。

## 常见影响范围

| 修改 | 必须重新检查 |
| --- | --- |
| 换酒店 | 每日首末路线、总通勤、酒店价格、公开隐私 |
| 换 POI | 相邻路线、营业/预约、餐饮区域、预算 |
| 改日期 | 营业、天气、票价、班次、预订链接 |
| 改返程票 | 最后一日顺序、行李、V5 缓冲 |
| 改人数 | 酒店房间、票价 quantity、餐饮和交通总价 |
| 改饮食禁忌 | 所有主餐厅与备选的人工复核 |

## 冲突处理

- 官方信息与攻略冲突：采用官方信息；
- 用户新要求与旧要求冲突：指出冲突并让用户选择；
- 价格来源过期：标记过期并重新查询；
- 无法重新查询：保留旧值但标记查询时间和不确定性。

## 双输出一致性

首次规划和每次更新都必须同时包含：

- `render_markdown.py` 生成并在聊天中完整呈现的攻略；
- 基于同一 JSON 重新渲染的 HTML 文件。

在攻略前简要说明改了什么、哪些来源重新核对及校验结果即可。不要用改动摘要、HTML 链接或已验证的公开 URL 替代完整对话版攻略，也不要输出冗长的工具清单或虚构“已部署”。
