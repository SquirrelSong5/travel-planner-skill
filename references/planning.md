## 1. 先固定不可移动项

按约束强度排序：

1. 已出票的航班/火车和入住退房；
2. 限时预约、演出、闭馆日；
3. 用户必去与明确禁忌；
4. 区域、节奏和餐饮偏好；
5. 可替换的普通候选。

任何候选与前三级冲突时，优先换候选，不要压缩安全缓冲。

## 2. 建候选池

为每个候选记录：

- 名称、类别和区域；
- 坐标；
- 建议停留时间；
- 开放/预约/票价证据；
- 适合时段；
- 天气敏感性；
- 用户兴趣匹配；
- 可替代候选。

攻略负责发现，高德确认位置，官方确认可用性。查不到坐标或开放信息的核心候选不要直接进入最终日程。

### 2.1 五源协作

完整攻略按平台属性交接，不让五个平台重复回答同一个问题：

1. 小红书先发现分区、节奏和近期体验风险；
2. 官方渠道确认候选的开放、预约和临时规则；
3. 高德确认坐标并把候选排成可行路线；
4. 美团围绕已经确定的每日区域补餐饮候选，再由高德确认位置；
5. OTA 核对酒店、票务、价格和可订状态；
6. 交付前用官方、高德和 OTA 复核易变事实。

五类平台各自在 `source_coverage` 中保留一项。完整多日攻略应尽量全部为 `used`；无法访问或不适用时记录原因，不得用搜索摘要或模型记忆冒充平台结果。

## 3. 按区域分日

- 普通日围绕一个主区域；
- 跨区必须有明确收益，并写出转场方式与时长；
- 相邻 POI 按地理位置和营业时段排序；
- 每日保留空白时间，不把所有间隙填满；
- 餐厅靠近主区域，或明确加入当天路线。

建议强度：

| 节奏 | 每日主要 POI | 适合 |
| --- | --- | --- |
| 轻松 | 2–3 | 老人、儿童、度假 |
| 标准 | 3–4 | 大多数城市旅行 |
| 紧凑 | 4–5 | 体力好、停留短 |

数量不是硬规则。大型主题乐园、博物馆或远郊景区可能占一整天。

## 4. 处理交通

每个主要移动段保存：

- `from_idx` / `to_idx`；
- `mode`；
- `duration_min`；
- 人读描述；
- `source` 与 `source_ref`；
- 可用时保存票价或打车区间。

`idx = 0` 表示酒店。不要只写 POI 之间的移动而漏掉普通日的酒店出发与返回。

选方式时结合距离、换乘、行李、天气、同行人和末班车，不用固定公里阈值替用户做所有决定。

## 5. 安排餐饮

- 午餐和晚餐各给一个主选；必要时给一个近距离备选；
- 主选必须有坐标；
- 避开与下一项预约冲突的排队型餐厅；
- 对忌口、过敏、清真、素食等做人工复核；
- 价格带 `unit`、`quantity`、`source` 和查询时间。

## 6. 最后一日倒排

从实际返程票出发时间倒排：

- 国内航班通常至少预留值机/安检与机场交通缓冲；
- 节假日、跨城机场、托运行李和老人儿童需增加缓冲；
- 最后一项活动的结束时间必须早于出发；
- 行李存取与酒店到枢纽的路线要显式存在。

不要误用去程票计算返程缓冲。

## 7. 天气与备选

临近出发才能获得可靠天气时，先保存季节性风险；有预报后更新：

- 雨雪/高温/大风影响的户外 POI；
- 室内备选；
- 日出、夜景、缆车和水上项目条件；
- 交通中断或景区临时关闭。

## 8. 完成定义

最终方案应同时满足：

- 关键硬事实有来源；
- 主要路线已查询；
- 时间表留有现实缓冲；
- 价格没有伪造来源；
- 五类平台都在 `source_coverage` 中记录了实际用途和使用状态；
- 预订状态、Plan B、安全提醒和行前复核节点完整；
- 严格校验通过；
- Markdown 与 HTML 均从最新 JSON 生成；
- HTML 实际打开检查过；
- 公开发布经过用户确认。
