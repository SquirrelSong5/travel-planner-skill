# 酒店规划

酒店不是独立选项，而是每天路线的共同起点。先选区域，再选具体酒店。

## 输入

- 每晚预算、房间数和人数；
- 已订酒店及能否取消；
- 主要 POI 区域；
- 机场/车站到达与离开时间；
- 行李、老人儿童、无障碍和夜间出行需求；
- 对地铁、打车、早餐和房型的偏好。

## 区域评分

优先考虑：

1. 多数日期的通勤总量；
2. 到机场/车站的稳定性；
3. 晚餐后返回便利；
4. 夜间环境与步行安全；
5. 房价、取消政策与真实房型；
6. 地铁口不是直线距离，而是实际步行入口。

不要只因为“市中心”就推荐，也不要只看酒店评分忽略路线。

## 是否换酒店

默认不换。只有以下收益明显时才考虑：

- 行程形成两个相距很远的区域块；
- 连续多日可显著减少长距离往返；
- 早班交通必须住在枢纽附近；
- 度假型住宿本身就是核心体验。

同时计入换住成本：退房、寄存、搬运行李、入住等待和不可取消风险。只省一次 20–30 分钟通勤通常不值得换住。

## 数据要求

酒店至少包含名称、地址、经纬度和选择理由。若展示价格，保存晚数、房间数、含税口径、取消条件、来源和查询时间。

每个普通日检查：

- 酒店 → 第一站；
- 最后一站 → 酒店；
- 第一天到达枢纽 → 酒店；
- 最后一天酒店/行李 → 离开枢纽。

`scripts/add_hotel_legs.py` 可补路线，但必须显式使用 `--output` 或 `--in-place`，避免意外覆盖原始数据。
